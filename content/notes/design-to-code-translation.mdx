# The last ten percent is usually where the real frontend work starts.

The first version of a website is rarely the difficult part.

Getting the page on screen is usually straightforward. The interesting work starts when the design meets real content, real browsers, existing WordPress plugins, Shopify behavior, caching, third-party scripts and a phone that is not the size of the design file.

## Bugs rarely live where you expect them

A broken layout can come from a CSS rule, but it can also come from a parent creating a new containing block, a theme style winning the cascade, an AJAX response changing markup, a plugin adding a wrapper or a cached asset serving an older version of the page.

I have learned to debug from the browser outward instead of immediately rewriting the component that looks suspicious.

## I check the rendered result first

Before changing code, I want to know what the browser actually received.

That means checking the DOM, computed styles, network requests, console errors and the element's ancestors. On WordPress projects, I also check whether a theme or plugin is adding behavior I did not write.

That small discipline prevents a lot of blind CSS changes.

## Responsive bugs are often relationship bugs

Something being 12px too far to the left is not always a 12px problem.

It can be the wrong container, an unexpected width, a flex alignment rule or a parent with overflow. Fixing the relationship instead of the symptom is what keeps the fix from breaking another viewport.

## Production-ready means boring in the right places

I want the final pass to be uneventful. No unexpected horizontal scroll, no broken menu, no layout jump when content changes, no console errors that should not exist and no interaction that only works because the mouse happened to be in the right place.

The best debugging result is often invisible: the site simply behaves the way it should.
