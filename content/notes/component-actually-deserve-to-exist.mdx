# When the plugin is not the answer.

Working with WordPress teaches you very quickly that there is almost always a plugin for the problem in front of you.

Forms, filters, SEO, caching, custom fields, imports, redirects, accessibility, WooCommerce behavior — the ecosystem is huge. The harder question is whether adding another plugin is actually the right engineering decision.

## I ask what the feature really needs

If a plugin solves a broad problem that the site genuinely needs, it can be the right choice.

But sometimes the requirement is much smaller. A custom WooCommerce checkbox, a tiny frontend filter, a specific API response or a small admin workflow does not necessarily need an entire plugin with its own settings, scripts and update cycle.

In those cases, a focused piece of code can be easier to understand and maintain.

## The smallest useful solution usually wins

I try to avoid both extremes: installing a plugin for every small requirement and writing everything from scratch just to prove I can.

The useful middle ground is to understand the platform first. WordPress hooks, WooCommerce data, ACF, REST endpoints, browser events and existing theme behavior often give you enough control to solve a specific problem cleanly.

## Custom code still needs boundaries

A custom solution is not automatically better. It still needs sanitization, escaping, capability checks, predictable naming and a clear place in the codebase.

The point is not fewer plugins at any cost. The point is knowing what you are adding and why it belongs there.

## This matters even more on production sites

A feature that works on a development site is only part of the job. I also have to think about updates, caching, existing plugins, theme behavior and what happens when another developer has to touch the code later.

That is why I prefer small, explicit solutions when the requirement is small — and established plugins when the problem is genuinely bigger than a few lines of custom code.
