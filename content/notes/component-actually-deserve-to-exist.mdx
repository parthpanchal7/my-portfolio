# When does a component actually deserve to exist?

One of the easiest ways to make a frontend codebase harder to work with is to abstract too early.

A component feels productive because it gives a name to a piece of UI. But a name alone does not make an abstraction useful.

## Repetition is a signal, not a command

Seeing the same markup twice does not always mean it needs a component. Sometimes the differences are more important than the similarities.

I look for repeated structure, repeated behaviour, or a meaningful concept before extracting something.

For example, a `ProjectCard` can make sense when projects share a real interaction and visual contract. A `WrapperWithGap` component usually tells me that CSS has been replaced with ceremony.

## Prefer the smallest useful boundary

A good component boundary makes a change easier to reason about. It should answer a question such as:

> What part of this interface has its own responsibility?

That responsibility might be a navigation system, a form field, a project preview, or an interactive menu.

The boundary should not exist just because a file became long.

## Abstraction has a maintenance cost

Every reusable component introduces another API to understand: props, variants, defaults, composition rules and edge cases.

That cost is worth paying when it removes more complexity than it creates.

It is not worth paying simply to make a folder tree look sophisticated.

## Let the interface teach you

I prefer to build the first version of a UI with enough duplication to reveal its real patterns. After using it at a few sizes and states, the useful abstractions tend to become obvious.

The result is usually fewer components, clearer props and a codebase that reflects the actual interface rather than an imagined future one.

Good component architecture is not about extracting everything. It is about choosing where a boundary makes the work easier.
